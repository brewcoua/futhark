# b2

Manages the Backblaze B2 bucket [Velero](../operations/recovery.md) writes to, and the application
key it authenticates with. Applying this module leaves a bucket with the right lifecycle rules and
a freshly minted Velero key whose two values you then file into Infisical.

Both the bucket and the key were made by hand in the console before this module existed, so a
first apply on an existing account adopts rather than creates. See
[Adopting the existing bucket](#adopting-the-existing-bucket).

## Prerequisites

- A state bucket, an SSE-C key and two Proton Pass items, all created by hand. See
  [Before the first apply](#before-the-first-apply).
- The `tofu.b2` section of `config/sops/ops.sops.yaml`, written from its `.example`.
- The common module rules in [Rules for every module](index.md).

## Applying

```bash
just tf init b2
just tf plan b2
just tf apply b2
```

Verify: the plan is a no-op on a second run, and `just bak backups` still shows backups completing
once the new key is filed.

The bucket's name and region are not defined here. `refs.env` reads them from
`config/sops/cluster.sops.yaml`, the file Flux renders into the `BackupStorageLocation`. That CR fixes its bucket at render time, so Flux has to hold the name, and
this module provisions what it names rather than naming it a second time.

## Before the first apply

Create by hand, once:

1. A **state bucket** in B2: `allPrivate`, no object lock, distinct from the backups bucket.
2. An SSE-C key:

   ```bash
   openssl rand -base64 32
   ```

3. Two Proton Pass items in the vault. The `tofu.b2` section of
   `config/sops/ops.sops.yaml.example` names every field.

| Item                   | Holds                                           | Capabilities                                                                                                                         |
| ---------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `backblaze-tofu`       | the provider's key id and key                   | `listBuckets`, `writeBuckets`, `deleteBuckets`, `listKeys`, `writeKeys`, `deleteKeys`, plus every capability `keys.tf` grants Velero |
| `backblaze-tofu-state` | the backend's key id and key, and the SSE-C key | restricted to the state bucket: `listBuckets`, `listFiles`, `readFiles`, `writeFiles`, `deleteFiles`                                 |

Neither is the account's master key. An application key can hold `writeBuckets` and `writeKeys`,
and the master key is the one credential B2 refuses on the S3 API that the backend speaks. The
provider's key needs Velero's capabilities as well as its own, because a key can only mint a key
whose capabilities are a subset of its own.

## Adopting the existing bucket

The bucket already exists, so the first plan wants to create it. Import instead:

```bash
just tf init b2
just tf plan b2                                     # wants to CREATE the bucket, do not apply
just tf adopt b2 b2_bucket.backups <bucket id>      # id from the console, or `b2 bucket get`
just tf plan b2                                     # now a no-op but for lifecycle_rules
just tf apply b2
```

The old application key is not imported. Let the apply mint a fresh one, then follow
[Credential rotation](../operations/rotation.md#veleros-b2-key) from the filing step: file the new
key, prove a backup works, revoke the old key in the console, and prove a backup works again.

After this, every other operator machine needs `just tf init b2` and nothing else.

## Filing Velero's key

The module mints the key and stops there. Two `sensitive` outputs carry it, and Infisical
`/infra/velero` is where it goes. `infra/backup/app/secret.yaml` templates it from there into
Velero's credentials file.

```bash
cd tofu/b2
tofu output -raw velero_b2_key_id           # -> B2_KEY_ID
tofu output -raw velero_b2_application_key  # -> B2_APPLICATION_KEY
```

Replacing the key later is the same loop, forced. Both `capabilities` and `bucket_ids` force
replacement. The full procedure, with its verification and revoke ordering, is
[Credential rotation](../operations/rotation.md#veleros-b2-key).

## What `buckets.tf` sets, and what it does not

The bucket is `allPrivate`, has no object lock, and has no lifecycle rule touching live objects.
Retention belongs to Velero's `Schedule` and to Kopia's own maintenance. A B2-side deletion of a
live object corrupts the repository, and the corruption surfaces at restore time. The two rules
present only reap what Kopia has already abandoned: unfinished large uploads after a day, hidden
versions after 30.

## State is remote, and why

This is the one module whose state is not local, against the rule in
[Rules for every module](index.md#rules). `b2_bucket` can be imported by bucket id and nothing
else, and B2 bucket names are globally unique. On a second operator machine, empty state does not
mean "adopt the bucket", it means an apply that fails with `duplicate_bucket_name`. The state
lives in a B2 bucket instead, and any machine with the two Proton Pass items reaches it with
`just tf init b2` and nothing more.

That bucket is created by hand and stays unmanaged, because a module cannot create the bucket
holding its own state. Nothing in the repository names it. `TF_BACKEND_BUCKET` under `tofu.b2` in
`config/sops/ops.sops.yaml` is the only record, and `.just/tofu.just` passes it to `tofu init` as
`-backend-config`, so it is never written into a `.tf` file.

Two things about that backend are load-bearing:

- **SSE-C.** `b2_application_key.velero` puts a live credential in state in plaintext, which is
  exactly what the local-state rule exists to prevent. `AWS_SSE_CUSTOMER_KEY`, 32 random bytes in
  base64 from Proton Pass, makes the state object ciphertext Backblaze holds no key for. That is
  the same property [Backup and recovery](../operations/recovery.md) relies on for the backups
  themselves. Lose that key and you lose the state, not the backups. Recover by re-importing.
- **`use_lockfile = false`.** B2's S3 API does not honour the `If-None-Match` conditional write
  the S3 backend's lockfile is built on, so with locking on no apply ever acquires the lock. This
  is safe only because there is one operator running one apply at a time. If that stops being
  true, the lock has to come from somewhere else.

## The region check

`account.tf` asserts that the account's own S3 endpoint matches the region in
`config/sops/cluster.sops.yaml`. Nothing else does. Flux will happily render a wrong region into
Velero's `s3Url`, and the symptom is an opaque 400 with the `BackupStorageLocation` stuck
`Unavailable`, while the daily `Schedule` still reads green until the 26h alert fires. A `check`
block warns on plan rather than failing it, which is the right weight: a mismatch there does not
make the plan for the bucket wrong.
